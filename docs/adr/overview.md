Here is how the entire ecosystem is set up:1. The Core Full-Stack Web AppOriginally, I was planning a separate Node.js API and Next.js frontend, but I realized that was adding unnecessary complexity. Instead, I migrated everything into a unified Full-Stack Next.js Monorepo.The backend API is now built directly inside Next.js using App Router API Routes (src/app/api/).This means we only have to manage one single Git repository for the web application. It completely eliminates CORS issues, simplifies our hosting, and allows the frontend to hit the backend using clean, relative paths like fetch('/api/workers').2. Infrastructure & The Shift to FirebaseFor our database and authentication, we are using Firebase (Firestore, Auth, Storage). Because Firebase is a fully-managed cloud service, we don't have to deal with hosting or configuring local database engines like MongoDB or PostgreSQL on our development machines.3. Our Docker & Development StrategyBecause Firebase removes the need to coordinate local database containers, we don’t need a docker-compose file for our web app. We use a single, high-performance Multi-Stage Dockerfile at the project root.Our workflow is split to maximize productivity:Day-to-Day Coding: We don't code inside Docker routinely. We run npm run dev natively on our machines so we get instant, 50ms Hot Reloading. Because Next.js handles its own compilation and our dependencies are strictly locked via package-lock.json, there are no 'works on my machine' issues.Production Verification: Right before we push code to GitHub, we use Docker as a final sanity check. We run docker build and run the container locally with our .env keys. If it passes inside the Docker container, we know with 100% certainty that it matches production conditions and will deploy flawlessly.4. Mobile Applications & Secure Cloud BuildsWe also have a Flutter user app and a native Kotlin admin app. Just like the web app, we develop these locally using physical devices or emulators to keep features like Flutter Hot Reload active.When it comes to building and releasing them, I've set up a highly secure pipeline:Our private production .jks keystores and key.properties files are safely blacklisted inside .gitignore and .dockerignore so they never leak to GitHub.Instead, I’ve set up a GitHub Actions workflow. When we push to the main branch, a secure cloud runner grabs the code, safely decodes our keystore from encrypted GitHub Secrets (Base64), and compiles the project.The workflow automatically generates both the official Google Play Store .aab bundle and a shareable test .apk file simultaneously, which we can download right from the GitHub Actions panel.5. Keeping the Repo CleanLastly, I've swept away all the development clutter. I've added a global *.log catch-all safety net to our .gitignore to ensure that standard system logs or temporary Java/Gradle crash files (hs_err_pid*.log) never get accidentally tracked or bloat our Git history.Overall, it’s a super streamlined, secure, and production-ready setup. Anyone can clone the repo, copy the .env.example template, run npm install, and start coding instantly."
